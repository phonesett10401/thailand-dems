# Thailand DEMS — Supabase Backend Design

Date: 2026-10-10 · Status: approved in conversation, awaiting written-spec review
Builds on: `2026-10-09-ui-redesign-design.md` (Phase 1 citizen UI, merged to `main` at `e5d5ae0`)

## 1. Purpose

Move DEMS from local MySQL + Express to **Supabase (Postgres + Auth)** with the API living inside the SvelteKit app in `web/`, so the citizen site runs on **Vercel + Supabase** only, and replace the fake/plain-text logins with real accounts.

Success means:

- The deployed citizen site reads shelters, disasters, alerts and evacuation routes from Supabase and stores citizen reports there, through `web/`'s own `/api` routes.
- Admins and volunteers log in with Supabase Auth (email + password, invite-only). No plain-text password exists anywhere.
- All existing data (minus test leftovers and plain-text passwords) is in Supabase, with all 12 triggers' behaviour preserved.
- The anon/publishable key cannot read or write any table directly.
- The database can move to any other Postgres host by changing one URL.

## 2. Decisions (from brainstorming)

| Topic | Decision |
|---|---|
| Database | Supabase Postgres 17, single project `thailand-dems` (region Northeast Asia / Tokyo, chosen at creation) |
| API location | **SvelteKit server routes in `web/`** (`+server.ts`); Express retired at end of Phase 2 |
| DB driver | `postgres` (porsager) over the Supabase **transaction pooler** (port 6543, `prepare: false`); no `supabase-js` for data |
| Auth | Supabase Auth, **email + password, invite-only**, sign-ups disabled; Google sign-in later |
| Roles | `admin`, `volunteer` in `auth.users.app_metadata.role` (settable only with the secret key) |
| Volunteers | Migrated to Supabase Auth now; plain-text `Password` column not migrated |
| Data access security | RLS enabled on every table, **no policies**; table privileges revoked from `anon` and `authenticated` |
| This project's API scope | The 5 endpoints the citizen UI uses + report list for admins (guard test) + auth |
| Out of this project | Admin/volunteer pages (Phases 2–3), remaining ~30 admin endpoints (Phase 2), Google sign-in |

## 3. Architecture

```
Browser ──► Vercel: web/ (SvelteKit pages + /api/* + /auth/*) ──► Supabase Postgres (pooler :6543)
                                   └──────────── @supabase/ssr ──► Supabase Auth
```

- `backend/` (Express) and `frontend/` (Next.js) are **not modified**. They keep working locally against MySQL until Phase 2 retires them.
- `web/` stops calling `PUBLIC_API_URL`; `src/lib/config.ts` points `createApi` at same-origin `/api`. `PUBLIC_API_URL` is removed from `.env.example`.
- The sample-data fallback and offline banner stay: if `/api/*` fails (e.g. the free project is paused), pages show bundled sample data with the banner, exactly as today.
- `ssr = false` stays for citizen pages. `/admin/*` and `/volunteer/*` pages turn SSR **on** (`export const ssr = true` in their layouts) so auth checks run on the server before any page is sent.

### 3.1 Environment (never committed; `web/.env` locally, Vercel env in production)

| Name | Where used | Secret |
|---|---|---|
| `PUBLIC_SUPABASE_URL` | browser + server | no |
| `PUBLIC_SUPABASE_PUBLISHABLE_KEY` | browser + server (auth) | no |
| `SUPABASE_SECRET_KEY` | server-only: scripts (create users) and the runtime salt for report IP hashes (required on Vercel) | **yes** |
| `DATABASE_URL` | server-only (`$env/dynamic/private`) | **yes** |

`web/.env.example` lists the four names with empty values.

## 4. Database schema (`web/supabase/migrations/0001_init.sql`)

Generated from the **live** local MySQL database (not the conflicting historical `.sql` files), then reviewed by hand.

### 4.1 Naming

- Tables and columns in **snake_case** (Postgres convention; unquoted names fold to lowercase, so PascalCase would force quoting everywhere). Examples: `Shelters.ShelterName` → `shelters.shelter_name`, `UserReports` → `user_reports`.
- The API keeps the **current JSON shape** (PascalCase keys the UI already uses) by selecting explicit columns with aliases, e.g. `select shelter_id as "ShelterID", shelter_name as "ShelterName" …`. Changing the JSON shape is a later, separate decision.

### 4.2 Type mapping

| MySQL | Postgres |
|---|---|
| `INT AUTO_INCREMENT PRIMARY KEY` | `integer generated by default as identity primary key` (sequences reset to max id after data copy) |
| `ENUM('a','b')` | `text` + `check (col in ('a','b'))` |
| `DECIMAL(p,s)` | `numeric(p,s)` |
| `DATETIME` / `TIMESTAMP` | `timestamptz` (MySQL values treated as UTC on copy) |
| `TINYINT(1)` / `BOOLEAN` | `boolean` |
| `TEXT` / `VARCHAR(n)` | `text` / `varchar(n)` |
| `JSON` | `jsonb` |
| `ON UPDATE CURRENT_TIMESTAMP` | `before update` trigger `set_updated_at()` |

All 36 foreign keys are recreated with the same `on delete` behaviour.

### 4.3 Triggers (all 12, rewritten as PL/pgSQL)

| Table | Timing / event | MySQL trigger | Behaviour to preserve |
|---|---|---|---|
| `agency_activations` | before update | `set_activation_timestamp` | stamp activation time on status change |
| `agency_activations` | after update | `update_resources_on_activation` | update agency resource availability |
| `agency_activations` | before insert | `validate_activation_request` | reject invalid activation requests |
| `agency_resources` | after update | `track_resource_deployment` | track deployment counts |
| `relief_supplies` | before insert / before update | `update_supply_status_insert` / `_update` | derive supply status from quantity |
| `shelters` | before insert / before update | `update_shelter_status_insert` / `_update` | derive shelter status from occupancy |
| `volunteer_assignments` | after update | `update_volunteer_hours_on_completion` | add hours on completion |
| `volunteer_assignments` | after delete | `update_volunteer_hours_on_delete` | adjust hours |
| `volunteer_assignments` | after insert / after update | `update_volunteer_on_assignment_insert` / `_update` | set volunteer availability |

Exact logic is ported from each trigger's MySQL body (read via `SHOW CREATE TRIGGER` during planning), not re-invented.

### 4.4 Security

```sql
alter table <every table> enable row level security;          -- no policies created
revoke all on all tables in schema public from anon, authenticated;
revoke all on all sequences in schema public from anon, authenticated;
```
The server connects as the `postgres` role through the pooler, which bypasses RLS. The project was created with "Automatically expose new tables" **off** and "Enable automatic RLS" **on**.

### 4.5 New tables

- `volunteer_accounts.user_id uuid unique references auth.users(id) on delete cascade` replaces `password`. `username` stays for display/login lookup.
- `report_rate_limits (ip_hash text, created_at timestamptz)` with an index on `(ip_hash, created_at)`. `ip_hash` is SHA-256 of the client IP plus a server-side salt derived from `SUPABASE_SECRET_KEY`; raw IPs are never stored. Rows older than 1 day are deleted opportunistically on insert.

## 5. Data migration (`web/scripts/migrate-from-mysql.js`, run once)

1. Read every table from local MySQL (credentials from `backend/.env`, never printed).
2. Drop dev leftovers with the existing `dropTestRecords` rule (`/\btest/i` in any text field) and the blank report (all user fields null).
3. Skip `volunteer_accounts.password` entirely.
4. Insert in foreign-key order inside one transaction; reset identity sequences to `max(id)`.
5. Volunteers: for each `volunteer_accounts` row, create a Supabase Auth user via the Admin API (`SUPABASE_SECRET_KEY`):
   - email `<username>@volunteers.example.com` (reserved domain; demo people get no real email), `email_confirm: true`, `app_metadata.role = 'volunteer'`, random 16-character password;
   - store the returned id in `volunteer_accounts.user_id`;
   - write `username, password` lines to `web/volunteer-logins.local.txt` (gitignored).
6. Print per-table row counts MySQL vs Postgres; exit non-zero on any mismatch beyond the intentionally dropped rows.

The script is idempotent on an empty database and refuses to run if target tables already contain rows (prevents double import).

## 6. Authentication

- **Server client:** `hooks.server.ts` creates a `@supabase/ssr` server client per request with cookie get/set, then `event.locals.user` = verified user from `supabase.auth.getUser()` (not the unverified session), and `event.locals.role` = `user.app_metadata.role ?? null`.
- **Guards** in `src/lib/server/auth.ts`:
  - `requireRole(locals, role)` → throws `error(401)` when signed out, `error(403)` for the wrong role. Used by every protected `+server.ts` and `+page.server.ts`.
  - `/admin/*` and `/volunteer/*` layouts redirect signed-out users to their login page.
- **Pages (minimal in this project):**
  - `/admin/login`, `/volunteer/login`: email/username + password form using SvelteKit form actions; errors shown generically ("Email or password is incorrect").
  - `/admin`, `/volunteer`: a signed-in landing page showing who is signed in, a sign-out button, and "Admin console arrives in Phase 2" / "Volunteer tools arrive in Phase 3".
  - `/auth/logout`: POST action that signs out and redirects home.
  - All in the existing visual system (civic theme for both until Phase 2 introduces the ops theme), all strings via Paraglide in EN/TH.
- **Volunteer login by username:** the form takes a username; the server looks up `volunteer_accounts.user_id` → auth email, then signs in with email + password.
- **Creating admins:** `web/scripts/create-admin.js <email>` prompts for a password in the terminal (never an argument, so it doesn't land in shell history), creates the user with `role: 'admin'`. Admins can also be created in the Supabase dashboard (role then added by the script's `--promote <email>` flag).
- **Settings verified by the plan:** sign-ups disabled, email provider on.

## 7. API routes (`web/src/routes/api/…/+server.ts`)

| Route | Method | Auth | Replaces |
|---|---|---|---|
| `/api/shelters` | GET | public | Express `GET /api/shelters` (incl. computed `AvailableSpace`, `OccupancyPercent`) |
| `/api/disasters` | GET | public | `GET /api/disasters` |
| `/api/alerts` | GET | public | `GET /api/alerts` (incl. joined `DisasterName`, `DisasterType`, `DisasterSeverity`) |
| `/api/evacuation/routes` | GET | public | `GET /api/evacuation/routes` (still returns the sample routes; there is no routes table — they become a static JSON response, labelled SAMPLE in the UI as today) |
| `/api/reports` | POST | public, rate-limited (5 per 10 min per IP hash) | `POST /api/reports/create` |
| `/api/reports` | GET | **admin** | `GET /api/reports` (proves the guard; used by Phase 2) |

- Each route has its SQL in `src/lib/server/queries/<name>.ts` and validates input at the boundary (report: same enums and length limits as `src/lib/report.ts`, coordinates within ±90/±180).
- Responses keep the exact JSON shape of the Express versions (verified by a shape test against `src/lib/sample/*.json`).
- `src/lib/api.ts` `submitReport` posts to `/reports` again (same-origin), keeping the offline/rejected distinction; `429` maps to a new "Too many reports from this connection, please wait a few minutes" message.

## 8. Testing

- **Unit (Vitest):**
  - migration transforms (row mapping, dropped password, test-row filter, timestamp handling);
  - report input validation and rate-limit decision function;
  - `requireRole` outcomes (signed out → 401, wrong role → 403, right role → passes);
  - each route's handler against a fake `sql` tagged-template function (no real database).
- **Response-shape test:** route output keys and types match the committed sample JSON for shelters, disasters and alerts.
- **E2E (Playwright):** existing 28 tests keep passing with mocks moved from `localhost:5000/api/**` to `/api/**`; new tests for login form errors, guarded redirect, and the 429 message.
- **Live smoke script** (`web/scripts/smoke-supabase.js`, run manually, never in CI):
  - row counts match the migration report;
  - each trigger fires once on a throwaway row inside a rolled-back transaction;
  - the publishable key gets no rows from the Data API for every table (RLS/grants check);
  - an unauthenticated `GET /api/reports` returns 401.

## 9. Rollout

1. Apply `0001_init.sql` to Supabase (via `psql`/script using `DATABASE_URL`).
2. Run the migration script; review counts.
3. Run the smoke script.
4. Create your own admin account with `create-admin.js`.
5. Switch `web/` to same-origin `/api`; full test suite green.
6. Merge to `main` (owner approval before push).
7. Owner imports `web/` into Vercel (Root Directory `web`) with the four env values.

Express + MySQL remain untouched as a local fallback until Phase 2.

## 10. Out of scope

- Admin and volunteer **feature pages** (Phases 2–3).
- The remaining ~30 admin endpoints (moved in Phase 2 alongside their pages).
- Google sign-in.
- Supabase GitHub integration / automatic migrations (connect after `0001` is applied and stable).
- Changing API JSON field names to camelCase.
- **Citizen accounts (noted for Phase 2):** citizens stay anonymous now. If added later: a `citizen` role, self sign-up re-enabled with email confirmation + CAPTCHA, used only for extras ("my reports", saved province alerts, notifications); nothing that works anonymously today may require an account.

## 11. Risks

- **Free-plan pause after 1 week idle:** the site falls back to sample data with the offline banner until the project is restored from the dashboard. Acceptable for a portfolio; Pro removes it.
- **Region is Tokyo (~99 ms round trip from Thailand measured):** acceptable for a demo; recreating in Singapore later means re-running steps 1–4.
- **Trigger porting mistakes:** mitigated by the smoke script firing each trigger and comparing with MySQL behaviour.
- **Serverless + Postgres connections:** mitigated by the transaction pooler and `max: 1` connection per function instance.
- **Rate limit is per IP hash:** shared networks (schools, mobile carriers) share a budget; 5 per 10 minutes is generous enough for emergencies, and the limit lives in one constant.
